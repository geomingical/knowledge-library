Grok Bot 101

從咖啡問卷到簡報與郵件：建立會記憶、協作與請示的 AI 同事

本場用咖啡問卷串起資料、簡報與郵件三個代理，說明 Grok Bot 的單位不是一次性對話，而是有職責、記憶與雲端電腦的長期同事。人要定義成果、教會操作、設定批准邊界並處理阻礙；現場的反覆請示與表單權限失敗，也讓這套協作方式的限制具體可見。

議程講者：Roman Ugarte表定台灣時間 00:00–01:00繁體中文公開摘要

適合第一次使用 Grok Bot，或想把問卷、簡報、郵件等重複工作交給多個代理協作的知識工作者與團隊管理者。

重點章節實作與概念操作流程限制原始來源

用語先說清楚：本頁的「代理」是能代人使用工具、執行工作的 AI；「上下文」是它判斷事情時能讀到的背景資料。其他專門用語在下方詞彙區有白話解釋。

先看本場專門用語的白話解釋
Computer use / Linux VM
Computer use 是讓 AI 直接操作電腦畫面。VM 可想成雲端提供的一台獨立電腦，Linux 是它的作業系統；本場用它建立表單與編輯簡報，不只呼叫現成整合。
MCP / API
MCP 是讓 AI 接上外部工具的連接方式；API 是軟體彼此溝通的介面。缺少這類連接時，本場改由代理直接操作瀏覽器與應用程式。
Teach a task / skill
先錄製人類在代理電腦上的示範，再整理為可重用技能；本場示範把簡報飛入動畫的操作保存下來。
Routine
按指定時間重複執行的工作安排；例子包括每天九點摘要簡報變更，以及多個代理每週合作寄出更新。
Auto review
判斷動作風險並決定是否請求批准的機制；本場另加個人規則，實際攔下需先詢問的郵件回覆。
Agent to agent communication
代理彼此交換背景與工作結果的協作方式；可在一對一訊息或群組中觀察，並據此等待前置產物完成。
Share as template / Marketplace
將角色設定作為模板分享，以及尋找公開或團隊模板的入口；適合重用工作規格，但不等於複製全部歷史記憶。
Memory / S3 buckets
本場以 S3 儲存說明長期記憶；可透過指示修正。角色被複製時從新記憶開始，過期委派關係也需更新。

03

把概念接回真實示範

01 / 長期角色：保留工作背景，而不只保留一串聊天

本場把代理視為一個有職責的工作單位：同一個角色可以跨任務與專案持續使用，累積使用者的格式偏好、溝通方式及工作背景。這和每次開新對話、重新交代所有事情不同。角色可依專長拆分，也可依專案拆分；重點是讓它知道自己負責什麼成果，而不是只給一張零散待辦清單。

現場例子

Data Dan 負責資料，Slide Sonya 負責投影片，Email Ethan 負責郵件。Email Ethan 不只處理這次咖啡調查，也被用來整理本場簡報摘要；簡報代理則可換品牌與主題繼續工作，不必為每份簡報重新建立一個角色。

02 / Computer use：讓代理直接操作網頁介面

直接整合、MCP 與 API 並非唯一工作入口。本場透過代理自己的 Linux 虛擬機操作 Google Forms 與 Slides，讓沒有現成整合的介面也能納入工作。使用者可以開啟遠端電腦看進度，必要時接管操作。每個代理的電腦分開執行，雲端工作不依賴個人筆電一直開著，但服務本身的登入與分享權限仍須正確設定。

03 / Teach a task：先示範一次，再存成技能

遇到難以用文字精確描述的介面操作，可以在代理的電腦上啟用 Teach a task，親自示範並錄下流程。示範結束後，系統把觀察到的操作整理成可重用技能。這裡要分清楚：錄製時是人控制電腦，不是代理自己完成；後續能否正確套用，仍要看產物，不能只因技能已生成就視為任務驗收通過。

示範者開啟 Slide Sonya 的簡報，進入插入動畫功能，選擇飛入效果並播放確認，再停止教學。問答時重新打開生成的動畫技能，說明日後可要求把同一效果套到另一段文字或物件；回答沒有提供逐格辨識等底層細節。

04 / 角色說明與例行任務：把品質要求和觸發時間分開

角色描述適合放穩定的工作規格，例如簡報要用什麼字型、顏色，以及完成後需要回傳什麼證據。例行任務則處理何時執行與反覆執行的工作。把兩者分開，能讓同一角色在不同任務中維持一致品質，又不必每次手動發起。跨代理排程也可把摘要與寄送串起來，但本場只是示範設定及用途，沒有等到隔日驗證觸發。

Slide Sonya 被要求完成投影片後傳回截圖；接著提出每天早上九點摘要共享簡報有哪些變動、由誰修改。另一個例子讓 Slide Sonya 和 Email Ethan 每週合作，把簡報變更寄給主管。時間與交付物都比『每天幫我整理一下』更明確。

05 / 批准是執行邊界，不只是聊天裡的承諾

本場先在設定加入回覆郵件前必須詢問的規則，稍後實際看到動作被個人 auto review 規則攔下。問答補充，系統會用基礎分類機制判斷動作風險，使用者還能加上更細的限制。規則可以嚴格到建立資料夾也要批准，但每次中斷都會降低自主工作效率，因此需要按對外影響與使用經驗調整，而非一律放行。

06 / 代理間交接：群組可見性與相依順序

07 / 模板分享與角色複製，不等於共享所有歷史

Share as template 讓角色設定可以在團隊內或公開 Marketplace 流通，適合傳播品牌格式與常用工作方式；複製角色則能針對不同對象微調任務與語氣。必須把設定重用和既有記憶分開理解：後段問答明確說，複製代理會保留角色方向，但從新的上下文與記憶開始，不會帶走原本累積的全部記憶。

08 / 排錯要回報可觀察現象，而不是只說失敗

當工作不如預期，先講清楚想產出的結果、使用者遇到的現象與可能卡住的條件，再讓代理往回檢查。示範者也建議在修正正確時給具體回饋，讓之後的工作有可沿用經驗。這不是保證代理一定能自動排除問題；本場最重要的教訓反而是，產物已建立與外部使用者真正能使用，可能是兩個不同的完成條件。

現場例子

問卷轉成 QR 碼後，觀眾回報『no access』。示範者要求確認連結公開，讓代理檢查分享設定，而不是重寫整份問卷。等待時改用先前測試試算表推進圖表演示；後面沒有明確宣布這次觀眾問卷已修復並完成資料寄送。

09 / 企業存取取決於授權，不是有電腦就能進內網

觀眾問虛擬機能否使用企業內部工具，回答把條件放在可提供的憑證、VPN 與系統驗證方式上；以 MongoDB 存取及 1Password 整合說明可能入口。後續再說敏感輸入會經由產品內的視窗收集，而不是直接在虛擬機畫面輸入。這些是本場的產品說明，不是對任意企業設定都已完成部署或安全稽核的證明。

10 / 記憶需要維護，過期協作關係要主動更正

後段問答說記憶持久保存於 S3，但可以透過指示修改或要求忘記。持久並不代表永遠正確，也不表示角色會自動知道外部世界所有變化。尤其代理團隊成員被刪除後，曾經委派過它的協調者可能還沿用舊認知。學習重點是把記憶當成需要維護的工作背景，而不是一次寫入就再也不用檢查的權威資料。
