Grok Bot for Founders

把創辦人的工作交給一隊會累積經驗的 Bot

從客戶通話準備、產品變更追蹤，到競品研究與回饋原型，本場示範如何把創辦人的日常工作交給長期存在的 Bot，並讓成果互相流通。重點不只是多做幾件事，而是保住專注、速度與判斷品質；創辦人仍須決定哪些回饋值得做、授權到哪裡，以及如何驗證與控制成本。

議程講者：Shub Gaur表定台灣時間 07:30–08:30繁體中文公開摘要

適合需要兼顧銷售、產品與營運的創辦人，以及想把零散代理任務整理成持續工作流程的部門主管。

重點章節實作與概念操作流程限制原始來源

用語先說清楚：本頁的「代理」是能代人使用工具、執行工作的 AI；「上下文」是它判斷事情時能讀到的背景資料。其他專門用語在下方詞彙區有白話解釋。

先看本場專門用語的白話解釋
AI maturity curve
本場用來區分聊天、短期代理與長期 Bot 的發展框架；不是經實驗驗證的統一分級標準。
Compounding
同一 Bot 持續利用先前資料、回應與修正，改善下一次工作；重點是累積職責經驗，而非每次重建。
Telemetry
產品使用情形的紀錄，例如席次、活動與使用趨勢；本場把它放進會前研究，協助找出客戶需求。
Activation
使用者達到關鍵價值體驗的狀態；示範以分享範本給隊友作為事件，再觸發額度獎勵。
Routine / webhook
Routine 是可重複執行的工作；webhook 可讓事件或輸入觸發它，減少沒有新資訊仍高頻重跑。
Headless browser / DOM
問答提出以無介面瀏覽器操作頁面元素，減少反覆看截圖再點擊的成本；不是保證快過 API。
Context window
Bot 當前處理的上下文範圍；不同 Bot 不共用同一份上下文，即使它們能讀取共同檔案。
Cloud Agent
可獨立執行開發工作的雲端代理；本場由 Grok Bot 交付相關資訊，代理回傳後再由 Bot 檢查。
Stalk Bot
本場的競品研究角色；名稱依實際畫面核對。它蒐集競品變動，並實際操作註冊與使用流程，不是股票分析工具。
API / MCP
API 是軟體彼此溝通的介面；MCP 是讓 AI 接上外部工具的連接方式。本場以瀏覽器操作補足缺少這類連接時的工作。

把一次性任務變成會累積經驗的職責

講者把聊天機器人、做完即丟的代理與長期 Bot 分開：後者的價值在於持續吸收資料、修正做法，再用於下一次工作。創辦人應先盤點要委派的職責，而不是大量建立 Bot 後期待它們自行找到用途；保護專注與決策品質才是目的。

03

把概念接回真實示範

每個整理點都附原始回放的參考時間；示範結果不等於對所有情境的保證。

01 / 複利來自同一職責的反覆修正

本場所說的 compounding，不是保證模型自動變聰明，而是讓同一 Bot 持續保留任務經驗，下一次能參考之前的反應與修正。講者建議先花一至兩小時盤點日常工作，再按客戶、財務、行銷等專長分組。這是他的管理偏好，不是要求所有人都採同一組織圖；想只對話一個窗口，也可以考慮幕僚長。

現場例子

Close Bot 會讀通話逐字稿：若某次介紹的新筆記功能讓對方無感，下一份會前文件就應避免再次主推，除非重新變得相關。講者以兩三週累積說明這種效益，並非提供保證達成的訓練時程或量化成效。

07:25:29 ↗ 回放

02 / 會前 HTML 要回答『對方現在需要什麼』

準備文件不是把公司介紹抄在一起，而是把客戶身分、正在使用哪些功能、使用量上升或下降，以及網站的實際問題放到同一視野。Close Bot 依日曆例行準備，讓人在短短十五至二十分鐘的客戶通話前，先掌握值得深談的議題。講者說文件是給自己用，所以外觀不必完美；真正重要的是研究能否轉成有用對話。

現場例子

現場用 Northwind 化名與占位數字避免洩露資料，展示席次、會議活動、使用趨勢、風險及建議。網站走查也可能發現 cookie 橫幅遮住送出按鈕，這種可立即採取行動的發現，能成為比泛泛推銷更具體的開場。

07:35:03 ↗ 回放

03 / 啟用事件把支援延伸到下一步行動

若已知道產品的關鍵啟用行為，就能讓 Bot 在事件發生時採取後續動作，而不只是寄一般提醒。講者把這段放在支援之後：連上資料與帳務，才可能完成額度、獎勵等實際處理。這種端到端設計依賴足夠授權，並不是一句提示就自然具備權限；他在總結也限定於使用者自己能接受的存取範圍。

現場例子

筆記產品示例把『將範本分享給隊友』視為啟用事件，接著寄送含額度的電子郵件。現場提到一千美元，講者立即稱它是誇張例子；學習重點是事件、動作與回饋的連接，不是照抄金額或聲稱這樣一定能留住客戶。

07:39:34 ↗ 回放

04 / 產品日報必須包含『已經撤回』的功能

團隊交付速度變快，創辦人可能還在介紹一個已不存在的功能。Prod Bot 因此同時讀開發紀錄與實際操作產品，將 shipped 與 unshipped 都列出來，並指出需要刻意決定的介面或產品細節。截圖和走查影片讓閱讀者可以追查觀察依據；再接上指標，才有機會從知道改了什麼，進一步看到改動帶來什麼結果。

現場例子

講者先分享自己曾在客戶示範時指向已被移除的側欄功能，接著要求 Prod Bot 為航班預訂示範站產生日報。Bot 彙整 PR、Linear issue 與網站操作，提供更新摘要、撤回項目、截圖及走查影片，避免只依提交紀錄猜產品現況。

07:43:06 ↗ 回放

05 / 競品研究不只看公告，也走完註冊與使用

競品 Bot 把公開資訊與實際產品體驗放在一起：更新紀錄、X 貼文、徵才方向、新用戶引導流程與功能操作，都可能成為定位訊號。它每隔幾天執行巡查，有相關變動才通知。講者另外提到以流失紀錄找出轉用其他產品的客戶，再詢問原因；目的可以只是理解選擇，不必每次接觸都立即要求對方回流。

現場例子

示範指定 Notion 與 Craft。Bot 使用拋棄式信箱走 Craft 註冊流程、實際建立筆記，並用自己的 Notion 帳號完成郵件認證與操作。HTML 拆解頁載入不順時，講者改看已有內容與操作影片，沒有把等待畫面說成另一項功能。

07:45:24 ↗ 回放

06 / Proto Bot 加速實作，不替代產品判斷

Proto Bot 持有獨立產品帳號，能直接看到介面，原型因而有現況脈絡，不必只靠口頭描述。客服信箱、X 與電子郵件等回饋可以進入同一管線，再交給開發代理處理。講者同時劃出清楚的人類責任：是否採納回饋、要不要交付，仍由理解願景的創辦人判斷。實作速度快，並不等於每一則回饋都應自動上線。

現場例子

現場要求拉取最新客戶回饋，得到『Bot 範本分享按鈕不夠醒目』的示範需求。後續看到它啟動 Cloud 代理，講者在切回簡報前仍說它正在工作；因此這段證明的是任務啟動與處理方式，而非已部署成功的前後對照。

07:50:22 ↗ 回放

07 / Yap Bot 學的是文字語氣，敏感訊息先留草稿

Yap Bot 參考郵件、Slack 與 iMessage 中的溝通方式，並按排程持續更新，其他專家 Bot 需要對外文字時可以請它協助。這裡的 voice 指寫作與說話風格，並非展示聲音複製。講者特別保留草稿模式：敏感信件不直接送出，之後比較原草稿和人實際送出的版本，讓修改差異回流成為下次寫作的線索。

現場例子

畫面敘述中，其他 Bot 已會主動請 Yap Bot 幫忙用講者語氣溝通。另設雜務 Bot 查 Drake 專輯等零散問題，避免把隨機需求塞進專家上下文；若雜務研究真有工作價值，再明確請它把該段資訊交給 Prod Bot。

07:52:10 ↗ 回放

08 / 把成本問題拆成操作次數與觸發方式

瀏覽器能補上缺少 API 或 MCP 的缺口，但重複看畫面、截圖、決策與點擊通常更昂貴。講者建議優先用既有 API，也可在一次操作時觀察網路請求，找出可重用的呼叫方式。另一個成本來源是例行任務太密：與其盲目定時重跑，不如降低頻率或由 webhook、實際輸入觸發。問答補充 headless／DOM 操作，但沒有承諾速度勝過 API。

現場例子

講者指出有人把任務設為每十五分鐘執行一次，等於一天近百次；若沒有新事件，這些執行仍在消耗資源。他也提議設立專門優化其他 Bot 的角色，檢查重複追問、失敗做法與排程，讓改善不只停在減少單次輸入。

07:57:49 ↗ 回放

09 / 可驗證的決策樹不等於模型本身變成決定性

企業觀眾問的是模型外部、不可略過的規則或政策，講者回答先承認模型本身不具決定性，再提出用程式與決策樹承接規則，讓模型每次呼叫相應函式；也可要求 Bot 向另一個 Bot 取得許可。他用『扮演決定性』形容效果。整理者解讀：這不是外部政策引擎的完整示範，不能據此宣稱所有行動已受強制控制。

現場例子

問答中的具體做法是交給 Cloud 代理寫程式，把相關決策整理成流程圖，遇到該類決策就呼叫可驗證的程式。現場沒有進一步展示權限拒絕、規則被繞過時的處理或稽核結果，因此只保留這個設計建議與講者的限制說明。

10 / 同一隊 Bot 可以共用檔案，不表示共用記憶
