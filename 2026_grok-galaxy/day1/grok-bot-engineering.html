Grok Bot for Engineering

讓工程代理帶隊：從重現故障、追蹤急件，到附上修復證據

本場把 Grok Bot 放在工程協作的管理層：由它啟動與督導雲端程式設計代理，讓各 Bot 交接知識、共用作業手冊，並以截圖、效能數據與實際操作判斷成果。人仍須定義產品方向、拒絕不合適需求、處理授權；真正可委派的不是一句「趕快修好」，而是有明確邊界與成功訊號的工作流程。

議程講者：Lingxi Li表定台灣時間 03:30–05:00繁體中文公開摘要

適合已使用程式設計代理、開始同時管理多項工程任務，想把催進度、驗收與知識交接變成可重用流程的工程師與技術主管。

重點章節實作與概念操作流程限制原始來源

用語先說清楚：本頁的「代理」是能代人使用工具、執行工作的 AI；「上下文」是它判斷事情時能讀到的背景資料。其他專門用語在下方詞彙區有白話解釋。

先看本場專門用語的白話解釋
Cursor Cloud agents
在雲端環境執行工程工作的代理。本場由 Grok Bot 啟動、讀取進度與追加提示，讓人不必逐一管理執行細節。
first party integration
產品提供的直接整合。本場指可用工具呼叫管理雲端代理，而不必操作使用者介面來啟動或閱讀紀錄。
MCP
本場用於連接外部工具的整合介面，例如 Vercel 與 Slack；沒有這類入口的網站工作，則示範改用電腦操作。
routine
讓 Bot 依時間或訊號執行的固定工作。本場包括夜間稽核，以及 P0 任務每五分鐘查看雲端代理進度。
playbook
團隊共用的操作手冊。示範存於 Notion，由 Jenny 負責更新與公告，記錄 P0 和交付證據等工程規範。
P0 escalation
這裡的 P0 代表最高優先處理的急件，escalation 是升級處理。本場設定定期檢視，辨識偏離或浪費並介入；這是講者的具體設定，不是普遍標準。
context limit
Bot 當下能處理的上下文有上限。本場以角色分工與 Notion 任務狀態表，減少同時管理多項工作的資訊負擔。
feedback loop
以可觀察結果判斷成功或失敗，再決定繼續修正或交付的閉環。本場例子包含網站操作、UI 截圖與效能指標。
PR / CI
PR 是交給他人檢查與合併的程式碼變更提案；CI 是程式變更後自動執行的檢查。本場要求提案附上真正操作產品的證據，不能只看自動檢查是否通過。

03

把概念接回真實示範

每個整理點都附原始回放的參考時間；示範結果不等於對所有情境的保證。

01 / 第一方整合：管理進度，不只是代寫程式

Grok Bot 在這套配置中負責協調，雲端程式設計代理負責執行工程工作。前者能透過工具讀取執行紀錄、啟動任務與追加回覆，不必靠點選介面才知道進度。講者把「是否真的完成」也交給這一層判斷，但判斷基準來自人事先要求的證據，並不是代理回報完成就直接接受。

現場例子

講者描述：一輪雲端工作結束後，Bot 檢查是否附上截圖或改善前後的效能比較。如果缺少，就直接回覆雲端代理，列出還要補的內容，讓工作在人離開電腦後繼續。這是工作流說明，非當場展示所有缺件追補步驟。

04:00:33 ↗ 回放

02 / 夜間稽核：先研究，再產出有條件可合併的 PR

講者把夜間清理用於較低風險的程式碼品質問題，例如收斂模組、縮減冗長註解；夜間較少人提交，也較不容易衝突。研究代理先掃描整個多專案共用程式碼庫，範圍亦包括安全稽核，再安排改善工作。自動合併不是預設無限制放行，而是要符合事先定義的端到端證據與其他條件。

現場例子

現場安裝夜間稽核工程師後，講者不等夜間排程，直接請 Steve 開始稽核。稍後查看時，Steve 已啟動多個雲端代理並整理成果；再往後已有清理 PR 可供審查，也明說另一項工作仍在跑，沒有把全部任務都描述成完成。

04:12:17 ↗ 回放

03 / Slack 訊息也能是內部工具的介面

對單一步驟的內部操作，不一定要先建資料庫、驗證機制與獨立後台。講者用加入測試邀請名單為例：同事在 Slack 標註 Bot 並提供 email，由例行任務或 webhook 訊號觸發既定操作。省下的是額外介面與部署，不是省略授權；Bot 仍必須用安全方式取得目標服務的存取權。

現場例子

本場口述原本可用一兩小時做出內部儀表板，改用 Bot 後只需描述任務，讓員工在 Slack 送出 email 即可啟動邀請流程。原稿把目標服務辨識為「test fly」，此處不假裝已看到完整服務設定或實際邀請寄出的畫面。

04:14:13 ↗ 回放

04 / 分角色的理由是上下文，不是不同模型能力

講者自問：既然工程 Bot 都用同一模型，為什麼還要三個？答案是各類任務有不同工作流程、長期規則和上下文上限。依 UI、開發體驗與基礎設施分工，能讓角色沿用自己的記憶。幕僚長只掌握分工與路由，避免總管也背負每個專業流程的全部細節。

現場例子

講者說，即使把 UI 工作交給基礎設施 Bot，它仍可能做得出來；拆分是為了下一個基礎設施任務來時，不必重新拉回那一類指示。平常主要找幕僚長分派，只有必要時才直接與各工程 Bot 對話。

04:16:58 ↗ 回放

05 / Bot 帶 Bot 入職：交接要有內容與確認

從模板市集裝入的 Bot 並不知道你的組織工作方式。現場不是由人重新講一遍，而是命令已熟悉流程的 Craig 帶新成員入職。交接資訊包括 Notion 看板要求、什麼叫完成清理，以及工作如何推進各階段；新 Bot 再確認並吸收到記憶。可重用的關鍵是知識傳遞，而不只是增加一個名字。

現場例子

講者新增夜間稽核工程師，要求將它改名 Steve，並請既有工程 Bot 告訴它如何遵守工程流程。稍後讀到 Craig 已傳訊、雙方已互相確認，再請 Craig 通知 Steve 立刻開跑夜間稽核，不需要人逐項複製所有設定。

04:20:00 ↗ 回放

06 / 先查回報是真是假：computer use 提供實際症狀

現場收到「無法查看以前訂好的航班」這個需求時，第一個指令是確認它是否屬實，而不是立即生成修補程式。Bot 在自己的電腦中瀏覽網站，講者可以監看。這種操作也涵蓋沒有 MCP 可呼叫的網站流程；成功訊號必須來自實際頁面與功能，而非只靠文字猜測故障。

現場例子

講者詢問 flylowair.com 是否真的無法查詢既有航班。稍後 Craig 回報 /trips 是 stub，導覽卻仍連到那裡，因此沒有查看先前訂位的功能。原稿展示查證結果與後續派工，但沒有展示這個故障修復後的完整驗收。

04:26:17 ↗ 回放

07 / P0 是具體監督頻率，不是反覆說「急」

講者先警告，單說緊急可能讓代理跳過步驟或猜測答案，因此把 P0 定義成可執行的督導規則：Grok Bot 每五分鐘檢視雲端代理進度，遇到偏離目標、無謂等待等情況再打斷並給後續提示。這是他的示範工作流，不是所有團隊或所有產品通用的 P0 標準。

現場例子

具體例子是代理在另一個 shell 等非同步測試，用了 sleep 300；如果測試一分鐘就完成，其餘四分鐘就是浪費。講者把這種情況寫進監看要求，接著用 Reply 引用故障診斷，要求「Fix this issue urgently」並指定按 P0 處理。

04:27:43 ↗ 回放

08 / Playbook 有單一負責人，更新後還要通知

只讓 Craig 知道 P0，不代表其他工程 Bot 也已知道。講者另建立 Jenny 作為營運負責角色，要求它擁有 Notion 操作手冊並避免其他工程角色修改。Craig 提交新規則，Jenny 負責更新與公告。這使一項口頭決定轉成團隊共享的日常操作，而非散落在各自聊天紀錄裡。

現場例子

現場先由幕僚長新增並交接 Jenny，再請 Craig 把 P0 工作流寫進手冊，讓 Jenny 通知所有工程 Bot。之後講者查看訊息，確認 Jenny 已與其他 Bot 溝通，也通知 Craig 手冊更新；需要人決策時，Jenny 仍會詢問。

04:30:53 ↗ 回放

09 / Notion 任務表：讓二十個代理的進度可查

Bot 能一面聊天一面工作，不代表它能無限承載新任務。講者承認催促與同時工作過多會讓上下文流失，因此使用 Notion 任務資料庫，記錄每項任務和所在階段。Bot 接續下一件事前可回查狀態，而非在對話中持續保留所有雲端代理的細節；分角色與外部狀態表是互補做法。

現場例子

示範中 Steve 已有一個清理 PR，另一項工作仍在進行。講者接著指出任務表記錄工作階段，並談到缺陷與安全檢查可找出代理引入的問題，例如資料外洩或 session 管理。原稿中部分欄位名稱辨識不清，故不杜撰完整狀態機。

04:34:48 ↗ 回放

10 / 回饋閉環：完成的依據必須可觀察

本場最終把工程委派收束到成功與失敗訊號：Bot 必須能判斷應該繼續催促，還是停止並交付合併。UI 改動看截圖，效能改善看指標，網站功能則可用實際操作形成回饋。講者強調連硬體工程也需要自己的可觀察訊號，但沒有在這場展示硬體測試流程。

現場例子

講者追加操作手冊規則：每個 PR 都附證據，UI 附截圖、效能工作附 metrics。後面實際查看一個上台前已啟動的任務，指出其中有成果截圖及 Bot 撰寫的雲端提示；那不是剛剛 /trips 急件已修好的證明，兩者不能混寫。

從工程 Bot 入職到以證據驗收：依現場操作整理的六步流程

05

哪些地方不能直接照單全收

分清楚現場示範、講者判斷與整理者提醒。

不要把急件變成猜測或省略步驟

講者明確提醒，「urgent」可能誘使代理為了快而跳過步驟。本場的修正是定義督導頻率、可打斷情境與後續提示，而非允許降低驗收標準。sleep 300 是說明等待浪費的例子，並未展示現場真的打斷了該命令。

04:23:24 ↗ 回放

自主不等於不用人做決策或授權

講者仍處理產品方向、架構、困難效能問題，並教 Bot 拒絕不適合的需求。登入、人類驗證與不願交出密碼的情況，可由人接管遠端電腦完成；提到可接管並不代表已替所有服務建立安全授權。

04:09:58 ↗ 回放

排程、合併與值班門檻都是個人設定

講者描述自己的夜間研究設定為凌晨三點，現場安裝的稽核 Bot 又說通常凌晨四點執行，不能合成一個產品預設。CI 約十分鐘未解決才通知值班者也是其工作流範例；自動合併的前提仍是預先設定的條件與證據。

多人工作仍會碰到上下文上限

講者承認，在 Bot 執行工作時頻繁催促或塞太多任務，可能讓它失去上下文。因此才用分角色記憶與外部 Notion 狀態表。這些安排是降低管理負擔的方法，不能解讀成任意數量的並行任務都能穩定完成。
