Grok Bot for Customer Support

把客服回覆做成有依據、可交接、需核准的工作流程

本場以虛構航空公司的客服環境，示範如何讓 Grok Bot 查閱知識庫、判斷是否足以回答、交接例外案件，並在 Stripe 沙盒（不動用真實金流的測試環境）處理退款。重點不是一次放開所有權限，而是從單一流程與唯讀開始，保留來源、人工核准及執行紀錄，再逐步擴大自動化範圍。

議程講者：David Gan表定台灣時間 07:00–08:00繁體中文公開摘要

適合客服營運、支援工程與知識庫負責人，尤其是想導入客服代理，又需要控制對外回覆、退款與文件修改風險的團隊。

重點章節實作與概念操作流程限制來源與公開範圍

用語先說清楚：本頁的「代理」是能代人使用工具、執行工作的 AI；「上下文」是它判斷事情時能讀到的背景資料。其他專門用語在下方詞彙區有白話解釋。

先看本場專門用語的白話解釋
Connector
連接器，讓機器人讀取或操作既有工具。本場涉及工單、文件、通訊與資料庫；接上工具不代表已取得所有寫入權限。
Routine
依排程或事件啟動的工作安排，例如每小時查看特定風險工單，不必每次都由人在對話中手動要求開始。
Knowledge base
知識庫，集中保存代理回答時依據的文件。示範區分公開產品說明與內部退款規則，兩者不應一律對外揭露。
SOP
標準作業程序，說明某類工作如何處理及哪些條件允許操作。本場以內部十四天退款規則作為簡化示例。
Handoff
交接，將代理目前不能可靠解決的案件交由人或其他處理者接手；需要保留原因，並不代表問題已經解決。
Evals / traces
Evals 用案例評估改動；traces 記錄每次執行的耗時及來源。兩者用來除錯與觀察，不等同已證明系統完全可靠。
Sandbox
沙盒是與真實客戶及金流隔離的測試環境。Stripe 畫面明示此模式，因此本課的退款與取消不是正式交易。
PR / code owner
PR 是提出變更供審查的請求，code owner 是負責審核相關內容的人。本場用它們說明知識庫更新的批准流程。

03

把概念接回真實示範

每個整理點都保留回放參考時間；示範結果不等於對所有情境的保證。

01 / 角色分工是成長後的選擇，不是起步門檻

Build、Reply、Alert、Tune 是這場示範的職責配置，不是產品要求每個團隊必須建立的四種角色。講者建議先教一個機器人跑通一條流程，等範圍變大或需要同時工作時才拆分。這讓團隊先釐清工作本身，再處理協作與權限，而不是一開始就承擔多個代理互相傳話的複雜度。

現場例子

現場由 Reply 判斷工單能否回答，遇到企業登入阻塞時通知 Alert，再由 Alert 發到 Slack；Tune 則用於補充 FAQ。這些分工有各自的觸發情境，講者沒有要求初學者先把四個機器人全部建好才開始使用。

02 / 把回覆變成可追溯的決策流程

知識庫提供依據，代理流程則規定如何使用依據。兩者不能混在一起：先讀工單、找相關知識，再決定回覆或交接，執行後留下備註。備註中的問題分類、信心與來源可讓人檢查回答基礎；這是可觀察的處理紀錄，不代表能讀取模型完整的內部推理。

現場例子

Alex 問如何重設密碼，工單中出現高信心判斷、問題根因及公開文件連結，回答步驟也對應文件。不過同一畫面有郵件寄送遭抑制的錯誤，因此只能說回覆文字已建立，不能因此推定客戶收到郵件。

03 / 低信心交接也可以是正確的產出

客服自動化不必把每張工單都回答掉。資料不足時，明確留下原因並移交處理，比猜測一個看似完整的答案更符合這場示範的規則。交接與告警又是不同動作：前者說明案件仍需處理，後者把符合重要條件的案件主動送到團隊正在看的通道。

現場例子

Ben 的 SSO／Okta 問題未被示範用的小型知識庫涵蓋。Reply 即使收到「試著回答」的要求，仍回報缺乏公開文件與內規、轉交人工；企業客戶無法登入的條件又讓 Alert 通知 Slack，而不是把未解決案件包裝成已解決。

04 / 退款需要政策、客戶狀態與動作權限一起成立

光有退款規則還不夠，代理必須找到正確客戶，讀取訂閱狀態，再在允許的權限內操作。現場採用十四天期限作為簡化案例，也說明可以要求人在執行前批准。Stripe 畫面明示這是沙盒；取消、退款與金額都是測試資料的變化，不能寫成真實付款處理。

現場例子

Carter 剛訂閱而獲示範退款，Damon 約訂閱二十天而被拒。講者補上客戶 ID 後再刷新 Stripe，比對前後狀態；Damon 的回覆只是提出可安排期末取消，畫面狀態維持原樣，並未展示已執行這項取消。

05 / 知識缺口與政策制定必須分開

發現文件沒有答案，不等於代理獲准自行創造一條規定。改善代理可以提出補知識的需求，但本場由人決定政策內容並授權修改，然後才重新回答工單。這道核准控制的不只是當前答案，也控制後續所有引用該文件的回覆，避免一次猜測變成團隊長期依據。

現場例子

Elena 問通行證能否與另一人共用。Reply 先停止回覆，建議 Tune 補 FAQ；講者明說不允許並要求新增，Notion 以綠色文字顯示政策。重新執行後，Reply 才有可引用的章節，並據此形成回答。

06 / 同一知識庫可以服務同事，但寫入權限仍需處理

內部客服同事需要的是完整作業規則，外部客戶則不應收到所有內部文件。講者用 Slack 示範讓同事詢問退款 SOP，讓既有知識資產不只用於客戶答案。然而連接到 Slack 不代表每個機器人都能直接發文；現場仍出現批准要求，權限與執行等待必須納入流程。

現場例子

07 / 從唯讀到寫入，按機器人分配權限

唯讀表示只能查詢，不直接改資料或對外發送；寫入則包含更新文件、退款與發訊息等會改變外界狀態的動作。講者建議先唯讀，再逐步開放寫入，特定動作保留人工核准，並讓不同機器人擁有不同權限。便利性不應被誤解成必須對整隊一次授予全部能力。

現場例子

Slack 示範中的批准比講者預期更保守，他仍指出對寫入來說這通常比較好。同一團隊中，一個機器人可以自動發 Slack，另一個則仍要先詢問；這是現場結語給的配置方向，不是完整企業權限管理介面的展示。

08 / 用評估與執行紀錄定位問題，而非只看最後答案

Evals 是用固定案例檢查改動是否仍符合要求；traces 是每次執行留下的可查紀錄。講者在問答描述將兩者存進 Postgres，包含耗時、讀過與最後採用的文件，讓人判斷問題出在查找還是回答。即使只寫草稿、內部問答或試跑，也應保留紀錄；資料表內容並未在台上實際展示。

現場例子

講者表示透過 Supabase 連接器讓 Build 建立評估與追蹤資料表，再要求每次 Reply 執行時寫入。之後可讓改善代理回顧這些紀錄找出修正方向。這是對自己設定方式的說明，不能稱為本場已驗證的自動改善成效。

08:02:38 ↗ 回放

09 / 把知識修改放進可審核的版本流程

回答企業非技術人員的風險疑慮時，講者提出受限範本與 GitHub 的版本管理做法。知識變更先開分支與 PR，經 BugBot 檢查、通知負責人、執行該分支的評估，再由有責任的人批准。這把「能提案」與「能直接改正式知識」分開，但現場沒有完成部署或安全保證的展示。

現場例子

講者描述讓改善機器人必須建立 PR，不能自己直接改知識庫；評估也可針對 PR 分支執行，而不是只對主分支。負責人因此能先看到改動後的回答表現，再決定是否合併，保留非技術同事參與改善的空間。

10 / 精確識別碼減少查找，不等於保證批次更便宜

只說「回答 Alex」會讓代理先取得未結案件、搜尋姓名，再找出應處理的工單。給明確工單 ID 能縮短這段資料定位工作。講者另外把低複雜度案件分組後用腳本批次處理；兩者都可能省用量，但仍取決於分類、紀錄與評估的工作量，不能把個人觀察當成固定單價。

現場例子

現場退款等待時，講者補上客戶 ID 以便更快找到資料；問答再以工單 ID 解釋相同原理。他自述一般中複雜工單約一至二美元，分組後的簡單案件約二角美元，並未提供樣本規模或每一項成本的明細。

04
