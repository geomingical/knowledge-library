讓 AI 代理值得信任

lauren（@poteto）談一個月送出 2,000 個 PR 的做法：先讓代理證明自己做對，再把經驗寫進程式碼庫

講者在 SpaceX AI 負責 Grok Bot，自述上個月送出兩千個上線的 PR，但這場真正的主題不是數量，而是「信任」：只有當你相信代理在你不在場時也會把事做好，才敢同時放出更多代理。講者給出三根支柱——讓代理能自己驗證、用技能教代理像資深工程師那樣做事、把程式碼庫改造成代理很難寫錯的樣子——最後收成一張「每次糾正代理時，該先改哪一層」的清單。

講者：lauren tan（@poteto）· Grok Bot @ SpaceX AI原為 Cursor Compile London 準備的演講影片長 38:01繁體中文學習筆記

適合：已經在用程式設計代理，卻發現自己得一直盯著、一直糾正它的人；以及想讓整個團隊（包括設計師、產品經理這些非工程師）都能放心交給代理改程式的技術主管。

核心重點開場信任曲線驗證品質技能五層清單Dune 與園丁米其林廚房收尾與行動限制來源

用語先說清楚：本頁的「代理」是能自己讀程式、改程式、跑指令的 AI 程式助手；「PR」是交給別人檢查、合併的一包程式碼變更。其他專門用語在下方有白話解釋。

先看本場專門用語的白話解釋
技能（skill）
放在專案裡、給代理讀的一份做事說明，可以附上腳本或工具。代理遇到相關任務時會照著做，像是交給新同事的一本操作手冊。
CLI
在終端機打字執行的小程式。講者把「啟動 app、收集證據」寫成固定指令，代理每次都用同一套，而不是每次自己臨時寫腳本。
Chrome DevTools Protocol
讓程式從外部遙控 Chrome 或 Electron 應用的介面，可以點按鈕、錄效能紀錄、拍記憶體快照。
效能追蹤／堆積快照
performance trace 記錄畫面在某段時間裡做了哪些工作、各花多久；heap snapshot 是某一刻記憶體裡有哪些東西。兩者都是找「為什麼變慢」的證據。
回歸（regression）
原本好好的東西，被新的變更弄壞或變慢。
靜態分析：lint、編譯器診斷、CI
不必真的執行程式，就先讀程式碼抓問題。lint 規則是團隊自訂的「不准這樣寫」；編譯器診斷是型別等錯誤；CI 是每次送 PR 時自動跑的檢查。它們都能自動擋下錯誤，不靠人記得。
Bugbot
Cursor 的自動程式碼審查機器人，會在 PR 上留言指出可能的錯誤。講者把它和「規則」歸在同一層。
形式化驗證（Lean、TLA+）
用數學方法證明程式「在任何情況下」都符合某些條件，而不是只測幾個例子。Lean 和 TLA+ 是這類工具的語言。
不變條件（invariant）
系統無論如何都必須成立的規則，例如「訂單金額不可為負」。
技術債（tech debt）
為了趕時間留下的權宜寫法，之後要花額外成本收拾。
鋪好的路（paved path）
團隊認可、唯一推薦的做事方式。路只有一條，代理就不用猜。
主程序／渲染執行緒
Electron 桌面應用分成兩塊：主程序管視窗和作業系統功能；渲染執行緒負責畫畫面。畫面那一側若被慢工作卡住，使用者就會感覺卡頓。
雲端代理、Grok Bot routines
雲端代理是在雲端機器上執行的程式設計代理；routines 是 Grok Bot 的例行任務，可以訂閱 Slack 討論串或錯誤警報，事件一來就自動開工。

先掌握這場的核心

五個重點，順序依演講的推進。每張卡片都附影片時間，方便回去核對原話。

瓶頸是信任，不是代理數量

多數人卡在同時只能盯 1–5 個代理：一離開，代理就做錯。沒有信任卻硬開上百個代理，只會得到一堆品質差的 PR 和上線的 bug。所以要先問「怎麼讓代理更值得信任」，再問「怎麼開更多」。

讓代理能證明自己做對了

講者的第一步是「驗證技能」：教代理自己啟動真正的 app、錄效能紀錄、收集證據。這個技能拆成兩半——CLI 讓代理能操作 app，功能地圖讓代理知道 app 有哪些功能、從哪裡進去。兩者合起來，代理就能驗證自己的工作。

程式碼庫就是代理的記憶

代理最愛延續眼前看到的寫法。好的寫法會被複製，壞的權宜寫法也會像病毒一樣擴散。所以要讓程式碼庫本身維持在「就算代理照抄也沒關係」的狀態，並讓錯誤寫法根本寫不出來。

不是軟體工廠，是米其林廚房

講者的論點是：把代理的工作環境設定得夠好，就能得到接近「個人或團隊軟體工廠」的東西——品質高、速度比以前快很多。但講者不喜歡「工廠」這個詞，因為做產品更像創作，不是在生產線上量產。

保母期最難離開

剛開始用代理時，每個對話都要看著、隨時介入糾正；人不在，事情就停擺或做錯。講者說這是最難脫離的階段，因為「怎麼離開」並不明顯。

跳級的代價

從 1–5 個走到上百個，差的不是按鈕，而是信任。沒有信任就派出一百個子代理或雲端代理，你會收到大量粗製濫造的 PR、一堆回歸錯誤與上線的 bug，沒有人會開心。

支柱一：驗證——讓代理自己證明做對了

06:51–12:33。投影片「我怎麼更信任代理？」列了三點：用驗證確保正確、用高品質技能教代理像真工程師工作（例如 pstack）、把架構重構成對代理友善。這一段講第一點。

今天就能做

驗證技能

教代理怎麼執行你的應用、用 Chrome DevTools Protocol 或其他除錯介面操作它、錄效能紀錄、拍記憶體快照。講者說只靠這一端，就能走很遠。

驗證的光譜
困難、仍是開放問題

形式化驗證

用 Lean、TLA+ 之類的工具，證明業務邏輯的不變條件永遠成立、應用永遠處在正確狀態。講者坦言真正做得到的人很少。

07:05 ↗ 影片

講者做的第一個技能：CLI ＋ 功能地圖

加入 Cursor 後，講者做的第一個技能是驗證技能：透過 Chrome DevTools Protocol 讓代理執行 app、錄紀錄。這個技能是一路改出來的，最後定型成兩個部分。

為什麼要把 CLI 放進技能

要代理每次都能「重現地」啟動 app、收集實際證據，證明程式能動、效能有達標。如果讓代理每次自己寫腳本，不同對話寫出來的都不一樣。把 CLI 做進技能資料夾，而且要持續投資、讓它能處理各種情況，代理才每次都用對的方法。

09:19 ↗ 影片

為什麼需要功能地圖

只有 CLI 還不夠。代理能開 app，卻看不懂模糊的問題回報，只能亂猜。功能地圖讓代理知道「使用者說的是哪個功能、要怎麼走到那裡」。

講者的例子

Slack 上有人回報問題，只貼了一小塊介面截圖，外加三個問號。只有 CLI 的代理完全不知道對方指的是什麼。加上功能地圖後，代理能理解內部同事與外部使用者送來的請求。功能地圖由一個自動化流程持續維護。

支柱二：用技能教代理像資深工程師那樣做事

12:33–14:56。驗證只回答「對不對」，還沒回答「好不好」。

正確性（驗證負責）

這個功能或程式碼，有沒有做到你要它做的事？例如：結帳按鈕真的能結帳嗎？驗證能拿到它確實能動的實際證據。

≠

品質（技能負責）

它的效能如何？程式碼寫得好不好？驗證本身說不太出來，需要教代理用真正軟體工程師的方法工作。

pstack：把個人工作流程打包成技能

講者做了一個叫 pstack 的外掛（plugin，一組技能的集合），今天沒細講。它的靈感來自講者做軟體工程這些年的工作方式：除錯、開發功能、做原型等各種任務，都有對應的做法說明，教代理照你想要的方式寫程式。

讓資深工程師寫進團隊技能庫

這是團隊裡資深工程師最能貢獻的地方：建立共用的技能庫，讓所有代理變聰明。技能加上驗證，代理不只能確認做對了，也能確認做得好——而且因為能真的跑 app，可以拿到真實的效能數據與統計。

支柱三：把架構改成對代理友善，以及糾正代理時的五層順序

14:56–18:57。第三點是把架構重構成對代理友善。講者說這可能是軟體團隊能做的最重要的事：如果你真心相信未來程式都由代理寫，程式碼庫就該設計成「預設就會做對」。講者在這裡帶出一張由硬到軟的五層清單（投影片旁註：新專案 vs 既有專案，講者未展開）。這張清單在收尾時再次出現，被講者指定為整場唯一要帶走的重點（見第 09 段）。

最常見的錯：只靠第五層

講者不建議只靠風格指南。看人類審查時留下的意見，是找出「缺了什麼」的好起點；但接著應該花時間把這些意見往前推到另外四層，而不是讓人繼續記。

比寫 lint 更好的做法

代理犯同一個錯時，可以加一條 lint 規則；「更好的是重構程式碼庫，讓這個錯變得根本不可能發生」。檢查是事後攔截，架構是讓錯誤沒有地方發生。

16:54 ↗ 影片
07

Dune：讓捷徑就是正路，並派一位園丁

18:57–30:38。Dune 是講者團隊為 Grok Bot 打造的「對代理友善的框架」，靈感來自 Cursor 代理視窗的效能教訓。重點不是 Dune 本身，而是它背後的想法。

代理愛抄捷徑，那就讓捷徑是對的路

他們得到的關鍵原則是：代理很愛走捷徑。那就把框架設計成「最簡單的那條路就是正確的路」。代價是這種程式碼庫對人類來說可能很煩，因為能做什麼、不能做什麼都被鎖得很死；但對只有很少背景資訊的代理來說，這是最理想的環境。

為什麼這很重要

未來改程式的人不一定是工程師：設計師、產品經理，甚至執行長，都可能直接進程式碼庫出功能。忙碌、沒什麼背景的人操作代理，也應該能預設做出好結果。

19:29 ↗ 影片

壞寫法會像病毒一樣擴散

程式碼庫是代理的記憶，這件事反過來也成立。一個小小的權宜寫法，或一段解釋權宜寫法的註解，代理很愛照抄；幾天或幾週後，它就到處都是，成了所有代理默認的慣例。

一個權宜寫法抄 →兩處抄 →十處抄 →變成「慣例」

投影片：「每一次複製，都讓下一次複製更可能發生。」講者也用花園比喻：看似無害的雜草，會長成一個難維護、效能問題一堆的「氛圍寫程式」（vibe-coded）程式碼庫。

20:43 ↗ 影片

最好的例子：Dune 禁止在程式碼裡寫註解

這個規則乍看很怪。人類寫註解是為了標記特殊情況、權宜寫法，或留言給同事。講者一開始也覺得代理留註解不算壞事，雖然很多都是廢話。

他們在 Cursor 程式碼庫看到的

代理會拿程式碼旁邊的註解當理由，說明「為什麼這裡不用真正解決問題」，然後貼一塊 OK 繃了事。於是 Dune 選擇禁止註解，免得代理複製這種模式、擴散到整個程式碼庫。

22:52 ↗ 影片

每個團隊都需要「園丁」

就像真正的花園需要有人留意雜草和害蟲，團隊也需要一個角色，專門在不想要的東西開始擴散前把它掐掉。Dune 的原則圍繞三件事：24:28 ↗ 影片

  1. 刪掉既有的技術債

    原因同上：留著就會被複製。

  2. 維持唯一一條鋪好的路

    大多數事情只有一種約定做法，代理就不用猜；程式碼庫、CI、lint 規則裡要有足夠的引導，讓代理走上這條路。

  3. 看到壞模式，第一反應是寫 lint

    不一定要馬上清掉。先寫規則「止血」，至少不讓它繼續長；之後再讓代理把它清乾淨。

  4. 心態：抄了也沒關係

    讓程式碼庫隨時處在「就算代理照抄，你也會滿意」的狀態。26:33 ↗ 影片

Dune 長什麼樣：用資料夾告訴代理規則

講者只快速帶過細節。Dune 有大量「程式碼該放哪、誰可以匯入誰」的約定。投影片列了五個名詞，每個在資料夾結構裡只有一個位置、執行時只有一個職責：

Feature

一個功能擁有自己的資料夾，放產品介面。

Entrypoint

使用者能打開的一個畫面，可以想成一條路由（網址）。

Transcript card

Grok Bot 對話畫面裡的一種卡片；每種內容的卡片本體由某個功能負責。

Client

畫面那一側的持久狀態，透過固定的函式與指令存取。

Host

在 Grok Bot 虛擬機上長期運作的行為，隔著有型別的介面呼叫。

27:11 ↗ 影片

畫面這一側（renderer）

功能介面、導覽、Client。這裡必須一直順：想要每秒 60 格，每一格只有約 16 毫秒；每秒 120 格只有約 8 毫秒。任何長時間工作都得切小塊做。

有型別的邊界

服務這一側（serving processes）

Host 擴充與 Electron 主程序，負責長期行為、視窗與作業系統功能。兩側共用的型別放在 shared/，每一側只能匯入被允許的層。

為什麼切得這麼死

這是 Cursor 代理視窗的教訓：有時候程式碼會不小心被匯入到畫面那一側，把畫面拖慢。Dune 透過「匯入的依賴關係圖」強制這條界線，從架構上把這種效能問題整類消滅。

27:47 ↗ 影片

投影片上的一句定義

「對代理友善，意思是：在打開的那個檔案裡做一個正確的修改，就能維持整個 app 的不變條件。」一個功能的介面元件永遠不必處理跨程序通訊通道、尋找 Host、重試順序或程序啟動。

29:18 ↗ 影片

核心教訓：過去藏在風格指南、資深工程師腦中、靠互相審查留言傳下來的「部落知識」，要抽出來寫進框架和程式碼庫本身。程式碼庫是你希望代理延續的那個狀態的具體快照；讓它乾淨到下一個代理自然會把好模式延續下去。29:47 ↗ 影片

08

米其林廚房：各層疊起來，再接上外圈

30:38–35:15。前面所有投資合起來，才是可以放手的廚房。

鎖得夠緊，連背景很少的代理也寫得好

程式碼庫、lint 規則、編譯器診斷、規則、Bugbot、技能，這些層疊在一起提供大量信任。在 Grok Bot 的程式碼庫裡，幾乎不可能寫出爛程式，所以即使背景很少、推理能力不強的代理進來，也能寫出好程式。

廚房比喻

如果發現某位廚師或洗碗工老是被同一個東西絆倒，當然要把它修好，別讓其他人也跌倒——廚房很危險。對程式碼庫也該是同樣的心態。

31:14 ↗ 影片

不需要「公司大腦」

有人會想建一個集中所有公司知識的系統。講者個人認為不需要那麼複雜：代理本來就很會用工具。把工具接到 Grok Bot，讓它自己去查，就能做出不錯的決定。

33:07 ↗ 影片

講者接著秀出 Cursor 團隊自動化流程的截圖：代理在 Slack 討論串裡自動重現 bug 回報、自動開 PR，替整個團隊增加價值。34:48 ↗ 影片

09

收尾：爬上信任曲線，照順序投資

35:15–38:01。回到信任曲線：把需要的每一塊都想清楚，就能更信任代理、平行處理工作，也讓團隊每個人（每位工程師、每位「建造者」）都能在這些基礎上高效產出。

「你會信任這個環境到一個程度，讓代理可以自由地去做。」「這不是什麼祕密，而是很多辛苦的工作。」— 講者，37:24 與 37:37 附近（中文意譯）

下次糾正代理時：一張檢查表

講者最後回到第 06 段的五層清單，說如果整場只能帶走一件事，就是這張投影片：每次糾正代理，都從這五層想，而且照順序想。

整理者依最後一張投影片與講者口述整理成可操作的步驟；講者建議「照這個順序想」。36:23 ↗ 影片

  1. 能不能讓這個錯寫不出來？

    改程式碼庫、架構或資料結構，讓錯誤寫法根本不存在。例如 Dune 用匯入規則，讓慢程式碼進不了畫面那一側。

  2. 不行的話，能不能自動擋下？

    寫成 lint 規則、編譯器檢查或 CI 檢查。就算還沒時間清掉舊的壞寫法，也先止血。

  3. 再用規則、Bugbot、技能引導

    把「該怎麼做」寫給代理讀，並讓審查機器人提醒。記得這層不保證每次都被遵守。

  4. 最後才留給人工審查

    人類審查的留言，拿來發現「還缺哪一層」，而不是長期依賴。

  5. 另外投資品質技能與驗證

    讓代理能跑真正的 app、收集證據，並依資深工程師的工作方式做事。

  6. 最後接上外圈

    信任建立後，才讓例行任務自動派出更多代理；否則只是更快地產出更多壞 PR。

哪些地方不能直接照單全收

分清楚講者的經驗、講者自己承認的限制，以及整理者的提醒。

PR 數量是自述，沒有品質數據

2,000／2,500／5,000+ 都來自講者自己的說法與貢獻圖，影片沒說怎麼計算，也沒有展示回歸率、退回率等品質指標。數量本身不是這場的論證重點，講者也說那不是目標。

新專案和既有專案的成本不同

Dune 是為 Grok Bot 新打造的框架，可以從頭鎖死規則。投影片旁註有「新專案 vs 既有專案」，但講者沒有展開。在大型既有程式碼庫裡做同樣的重構，成本與風險可能高很多（整理者提醒）。

禁止註解是 Dune 的選擇，不是通用規則

這是針對「代理拿註解當藉口」的具體對策。講者自己也承認這樣的程式碼庫對人類很煩。其他團隊要不要跟進，要看代理與人類各自在改哪些程式。
